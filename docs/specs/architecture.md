# 推奨システムアーキテクチャ

作成日: 2026-11-05 / 版: 1.0-draft / 状態: **提案・未承認**

## 1. 結論

単一リポジトリ内のモジュラーモノリスを提案する。データ、指標、戦略、約定、ポートフォリオ、評価、UIを分離し、重いバックテストはローカルPCのバッチ処理、Streamlitはスクリーナーと保存済み結果の閲覧を担当する。初期段階でサービス分割や別Webフレームワークへ移行しない。

これは設計提案であり、フォルダ作成やコード分割は今回行わない。

```text
データプロバイダー
  ↓
生データ・取得記録・ハッシュ
  ↓
正規化データ ─ 銘柄マスター ─ 時点別ユニバース ─ 企業行動
  ↓
共通テクニカル指標
  ↓
独立戦略モジュール
  ├─ 最新as-ofで評価 → スクリーナー
  └─ 過去as-ofを順に評価 → バックテスト
                              ↓
                   約定・コスト・資金管理
                              ↓
                   取引履歴・日次資産推移
                              ↓
                   評価・ベンチマーク比較
                              ↓
                  Streamlitダッシュボード
```

## 2. 論理コンポーネント

| コンポーネント | 責務 | 禁止する責務 |
| --- | --- | --- |
| domain | 銘柄、資産クラス、通貨、取引所、売買単位、注文、約定、ポジション | データ取得、画面表示 |
| data | プロバイダー、raw保存、正規化、母集団、企業行動、取引カレンダー | シグナル判断 |
| indicators | SMA、EMA、ATR、RS等の副作用のない計算 | 発注、ポートフォリオ参照 |
| strategies | 選別、セットアップ、エントリー候補、出口候補、理由コード | データ取得、UI、未来データ参照 |
| execution | 注文の有効時刻、約定価格、手数料、スリッページ、未約定 | 戦略選択 |
| portfolio | 現金、保有、資金配分、売買単位丸め、上限 | 指標計算 |
| backtest | 時系列の進行と各コンポーネントの呼出順 | 戦略固有の式 |
| analytics | 資産推移、取引統計、リスク、比較 | シグナル再計算 |
| artifacts | 設定、版、取引、資産、指標、警告、ハッシュ | 画面固有状態 |
| ui | 入力、可視化、成果物の読込 | 戦略式、約定、会計 |
| jobs | ローカル一括実行、データ更新、再現実行 | 対話UI |

## 3. 共通戦略インターフェース

スクリーナーとバックテストは同じ `evaluate(as_of, market_view, parameters)` 相当の純粋な判定処理を使う。具体的なPython APIは承認後の実装計画で決める。

判定結果には少なくとも次を含める。

- `strategy_id`, `definition_version`, `parameter_set_id`
- `instrument_id`, `asset_class`
- `decision_timestamp`, `data_cutoff_timestamp`, `earliest_execution_timestamp`
- `signal_type`, `side`, `strength_or_rank`
- 成立・不成立の理由コードと参照した指標
- 必要データ不足、ウォームアップ不足、取引不能の警告

バックテストは判定結果から注文候補を作り、ポートフォリオ規則で採否・数量を決める。スクリーナーは同じ判定結果を最新時点で表示する。戦略関数に全期間DataFrameを渡す場合も、`as_of` より後を物理的に切ったビューだけを渡す。

## 4. 戦略の合成単位

### 提案事項
- `UniverseFilter`: 個別株/ETF、上場状態、流動性
- `TrendFilter`: Trend Template、市場環境、RS
- `SetupDetector`: Anti、VCP、チャネル形成
- `EntrySignal`: クロス、ピボット、高値突破
- `ExitPolicy`: 固定損切り、チャネル、ATR、移動平均、時間、トレーリング
- `PositionSizer`: 等金額、等リスク、ATR/N、上限
- `StrategyComposition`: 上記IDとパラメータの固定された組合せ

この分離により、Trend Templateのような選別条件を単独の「買い」と誤認せず、同じエントリーに複数出口を適用できる。

## 5. 資産クラス設計

初期の株式・ETFは共通の現物約定モデルを使えるが、次を銘柄マスターに持たせる。

- 永続的な内部IDと市場ティッカー
- `asset_class`（equity / etf。将来拡張可能）
- 取引所、市場区分、通貨、タイムゾーン
- 上場日、廃止日、取引可能期間
- 日付で有効な売買単位
- ETFの場合は対象地域・資産、レバレッジ/インバース等の分類（取得可能な範囲）

将来のFXは株式モデルの条件分岐で実装せず、別の `ExecutionModel` と `AccountModel` を追加する。通貨ペア、pip、スプレッド、スワップ、レバレッジ、必要証拠金、強制決済を独立して扱う。

## 6. データと成果物

### 提案事項
- raw層: 取得した内容を変更せず、供給元、取得時刻、要求、ハッシュを保存。
- normalized層: 共通スキーマへ正規化し、調整前OHLC、調整係数、企業行動を区別。
- feature層: 指標は入力データ版、計算版、パラメータと対応付ける。
- run artifact: 実行設定、取引履歴、注文、日次資産、指標、除外理由、警告を一つの実行IDで束ねる。

DBやファイル形式は未決定。初期はローカルで扱える列指向ファイルと小規模メタデータDBが候補だが、依存ライブラリを含め承認後に選定する。

## 7. Streamlit統合案

| 案 | 保守性 | 実行負荷・費用 | 評価 |
| --- | --- | --- | --- |
| 同じ単一スクリプトへ全処理追加 | 低い | セッションごとに重い処理 | 非推奨 |
| 完全な別アプリ・別ホスティング | 分離しやすい | 運用先と費用が増え得る | 初期には過剰 |
| 同一リポジトリ、共通コア、Streamlit複数ページ、ローカルバッチ | 高い | 重い処理をローカルへ逃がせる | **推奨** |

推奨案では、Streamlitに「スクリーナー」「バックテスト実行設定（小規模またはジョブ作成）」「保存結果比較」「データ品質・警告」を設ける。モバイルでは要約カードと主要指標・警告を先に表示し、横長の取引表は展開表示またはダウンロードとする。具体的な画面仕様は未決定。

## 8. 通知への備え

通知処理は戦略を再実装せず、確定済みのシグナル成果物を読む。通知イベントには戦略版、判定時刻、最短約定時刻、理由、重複抑止キーを持たせる。送信先、時刻、再通知、認証、スケジューラーは将来仕様であり、初期実装には含めない。

## 9. 再現性と監査

各実行は、コード版、戦略版、データハッシュ、母集団、企業行動、約定・コスト、資金配分、取引カレンダー、IS/OOS区間、乱数シード、警告、出力ハッシュを含むマニフェストを残す。同一入力と版で取引履歴と指標が一致することを品質要件とする。
